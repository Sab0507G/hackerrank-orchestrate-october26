## 5. Failures found and improvements made

1. **Crash on unknown email.** An email that matches no user raised an IndexError, which would have failed the full run. Fixed: an authorized deletion with no matching identity returns COMPLETE with no steps. Found while writing custom_02.
2. **Spanish non-deletion phrasing.** "No borren nada" and "descargar mis datos" were treated as deletion. Fixed by adding those patterns. Found while writing custom_01. Only English and a few phrases in other languages are covered, so other languages may still be misclassified.
3. **Wrong NOT_APPLICABLE for real deletions.** NOT_APPLICABLE was assigned whenever no evidence matched, which wrongly excluded two authorized deletions (case_525, case_61). Fixed by deciding NOT_APPLICABLE from the request text only.
4. **Over-broad non-deletion patterns.** Three sample deletions were blocked by generic phrases ("copy of", "download", "please keep"). Narrowed the patterns. This was partly informed by the sample, so the hidden set may behave differently.
5. **Handover statuses ignored.** The shift-handover table's per-resource states were not used. Fixed by parsing them as authoritative state. Sample status 13 -> 17.
6. **Direct-identifier exposure.** SQL and JSON rows with only a user_id (tombstones, anonymized records) were treated as exposed. Fixed: exposure now requires an email, phone, hash, or name. Sample status 17 -> 18 together with the PDF and image fix.
7. **PDF and image evidence not read.** Fixed with pdftotext and tesseract, plus document-level resource extraction. Sample status 17 -> 18.
8. **User-id substring matching.** `user_1` matched inside `user_10`. Fixed with whole-word matching.

## 6. Known remaining failures

- **Missed findings (8 sample cases).** They come out COMPLETE when the answer key expects INCOMPLETE. The main cause is that the scanner does not link some remaining copies to the user, mainly deleted-account and analytics records that carry no identifiers.
- **False findings (3 sample cases).** They come out INCOMPLETE when the answer key says COMPLETE. The main cause is records still flagged as exposed when their state at audit_at is compliant.
- **Deleted-account linkage.** The answer key expects absence checks on deleted accounts. No principled link from a user to a deleted account is derivable from the activity stream, so those checks are missing. The pipeline does not guess one.
- **Gold uses later evidence in one case.** For case_09, the answer key relies on a log captured after audit_at. The spec forbids using it, so the pipeline excludes it, and this costs that step.
- **Non-English non-deletion requests.** Only some phrases are covered.
- **Weak step recall.** Step recall is 0.50, so even correct statuses often come with an incomplete step list.
